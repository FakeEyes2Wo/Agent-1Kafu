# 当前实现技术与流程文档

本文档描述当前方案的技术路线、数据流、运行流程、配置策略和实验流程。重点是方案如何工作、如何部署、如何生成提交结果，以及哪些配置适合做消融；不展开逐文件代码说明。

## 1. 方案定位

当前实现是一个面向客服问答比赛的 API-first RAG 系统。核心目标是在不本地训练、不本地评分的前提下，利用手册知识库、用户问题和可选图片输入生成符合比赛格式的 `submission.csv`。

默认路线是：

- 百炼 / DashScope API 负责大模型生成、视觉理解、可选 embedding 和可选 rerank。
- 本地程序负责数据读取、手册切块、BM25/sparse 检索、hybrid 融合、图片标记处理、缓存和提交文件生成。
- vLLM 不是默认必需项；只有改用自托管开源权重或微调权重时才需要本地部署。
- 不在本地做实际得分测试；本地只做格式、稳定性和流程验证，正式实验迁移到 GPU/API 服务器运行。

当前默认偏向“稳定提交”而不是“最大推理预算”：关闭 thinking，限制回答长度，保留可配置的 rerank、视觉和检索预算用于服务器消融。

## 2. 输入、输出与数据资产

### 2.1 输入数据

比赛数据主要包括：

- `data/question_public.csv`：公开问题集，生成提交文件时逐行读取。
- `data/submission_example.csv`：提交格式参考。
- `data/KownledgeBase/手册/*.txt`：商品或服务手册文本。
- `data/KownledgeBase/手册/插图/*`：手册图片资源。

用户 API 调用时的输入包括：

- `question`：客服问题文本。
- `images`：可选的用户上传图片，通常为 base64 或 data URL。
- `session_id`：可选会话标识，仅作为追踪字段，不读取持久化历史。
- `stream`：接口保留字段，当前统一返回非流式结果。

### 2.2 输出结果

比赛提交输出为项目根目录下的：

```text
submission.csv
```

字段固定为：

```csv
id,ret
```

其中：

- `id` 与 `question_public.csv` 中的问题 ID 对齐。
- `ret` 是最终客服回答。
- 若回答引用手册图片，正文中使用 `<PIC>` 占位，末尾追加图片 ID 列表。

API 服务输出为 `/chat` 的 JSON 响应，包含最终答案、会话 ID 和时间戳。

## 3. 总体技术架构

当前系统可以分为六个逻辑层：

1. 配置层

   通过 `.env` 管理 API key、模型、检索策略、预算、缓存路径和服务端口。

2. 数据预处理层

   读取手册文本，识别语言、标题、正文和 `<PIC>` 图片标记；将手册切成适合检索的文本片段，并记录图片 ID。

3. 检索层

   默认使用 hybrid RAG：本地 BM25/sparse 检索为基础，可叠加百炼 `text-embedding-v4` dense 检索，再通过融合和去重得到候选上下文。

4. 多模态层

   对用户上传图片进行视觉摘要；对手册图片通过 `<PIC>` 标记和邻近文本建立图片相关上下文，最终在答案中保留可提交的图片引用格式。

5. 生成层

   使用百炼 / DashScope OpenAI-compatible chat 接口生成初稿，再执行检查与改写，压制幻觉、格式错误和无证据承诺。

6. 产物层

   生成 `submission.csv`，同时保存检索上下文缓存和模型调用缓存，便于断点续跑、消融复用和结果排查。

## 4. 标准问答流程

单个问题的处理流程如下：

1. 接收问题和可选图片。
2. 如果存在用户上传图片，调用视觉模型生成图片摘要，并受 `VISION_MAX_IMAGES` 和 `VISION_MAX_TOKENS` 控制。
3. 判断问题类型：通用客服政策题优先使用通用政策上下文；商品手册题进入 RAG 检索。
4. 根据问题语言和关键词召回相关手册片段。
5. 若开启 dense embedding，调用 embedding API 获取向量召回结果。
6. 若开启图片检索，补充手册图片邻近文本片段。
7. 若开启 rerank，对候选片段重排，并截取最终上下文。
8. 将用户问题、图片摘要、检索证据和格式约束放入生成提示词。
9. 调用 chat 模型生成客服回答初稿。
10. 调用检查与改写步骤，删除无证据内容、冗余标题、目录噪声、错误图片 ID 和格式污染。
11. 对 `<PIC>` 引用做后处理，输出比赛要求的图片占位和末尾图片列表。
12. 保存模型调用 trace 和最终答案，写入 API 响应或 `submission.csv`。

这个流程保证每个问题独立处理。生成提交文件时不会读取上一题的会话历史，也不会把不同问题之间的信息串联起来。

## 5. 手册知识库处理流程

### 5.1 手册解析

手册文本会被解析为一批可检索片段。每个片段保留：

- 正文文本。
- 来源手册。
- 语言标签。
- 关联图片 ID。
- 可选 dense 向量。

手册里的 `<PIC>` 不直接交给模型自由发挥，而是被转换成受控图片引用信息。这样可以避免模型输出不存在的图片 ID，也方便最后统一转换为比赛格式。

### 5.2 切块策略

默认切块参数：

```env
CHUNK_SIZE=700
CHUNK_OVERLAP=120
```

切块越大，上下文更完整，但召回更粗；切块越小，召回更精确，但可能丢失步骤连续性。当前默认值偏向手册问答的可读完整性。

如果修改切块参数，需要重新构建索引。

### 5.3 索引构建

构建索引：

```bash
python scripts/build_index.py
```

索引产物：

```text
storage/vectorstore/index.jsonl
storage/vectorstore/index_meta.json
```

当 `RAG_BACKEND=faiss` 且 dense vectors 可用时，会额外生成：

```text
storage/vectorstore/index.faiss
storage/vectorstore/faiss_ids.json
```

`index_meta.json` 会记录当前 embedding、切块和 RAG 相关配置。关键配置变化后，系统会识别 metadata 不匹配并重建索引，避免旧索引污染结果。

## 6. RAG 检索策略

### 6.1 默认 hybrid RAG

默认配置：

```env
RAG_BACKEND=hybrid
TOP_K=8
RETRIEVAL_TOP_K=20
```

含义：

- `RETRIEVAL_TOP_K` 控制初始候选召回数量。
- `TOP_K` 控制最终放入模型上下文的片段数量。
- hybrid 模式会结合 sparse 和可选 dense 结果。

当前数据规模不大，因此默认仍使用本地 JSONL 索引和 BM25/sparse。系统已支持可选 FAISS dense 检索，但不默认开启；Milvus、Chroma 等外部向量库仍未引入。

### 6.2 Dense embedding

默认 embedding 路线：

```env
EMBEDDING_BACKEND=openai
EMBEDDING_MODEL=text-embedding-v4
EMBEDDING_BATCH_SIZE=10
```

百炼 `text-embedding-v4` 对 batch size 有限制，`EMBEDDING_BATCH_SIZE` 不建议超过 `10`。该参数主要影响构建索引速度，不直接提升答案质量。

没有 API key 时，系统仍可构建 BM25-only 索引用于本地流程检查，但正式提交建议启用 embedding。

### 6.3 FAISS dense 检索

FAISS 是可选 dense 检索后端，用于替代当前 JSONL 向量逐条 cosine 扫描。开启后，系统仍会保留 BM25/sparse、图片邻近文本和 RRF 融合；FAISS 只负责 dense 分支召回。

服务器安装：

```bash
python -m pip install -e ".[faiss]"
```

开启方式：

```env
RAG_BACKEND=faiss
EMBEDDING_BACKEND=openai
EMBEDDING_MODEL=text-embedding-v4
```

切换到 FAISS 后需要重新构建索引：

```bash
python scripts/build_index.py
```

FAISS 索引产物位于：

```text
storage/vectorstore/index.faiss
storage/vectorstore/faiss_ids.json
```

如果没有配置可用的 embedding API key，FAISS dense 分支不会启用，系统会退回 BM25/sparse 检索。FAISS 主要提升 dense 召回速度和后续扩展空间；在当前小规模数据上，它不保证直接提升分数，是否有收益需要结合 rerank 和上下文预算做服务器消融。

### 6.4 Rerank

rerank 默认关闭：

```env
RERANK_ENABLED=false
```

服务器消融时可开启：

```env
RERANK_ENABLED=true
RERANK_BACKEND=bailian
RERANK_MODEL=qwen3-vl-rerank
RERANK_TOP_N=8
```

rerank 的作用是从较大的候选集中筛出更相关片段。通常建议和更大的 `RETRIEVAL_TOP_K` 配合：

```env
RETRIEVAL_TOP_K=40
RERANK_TOP_N=10
TOP_K=10
```

相比开启 thinking，rerank 对质量提升更可控，也更容易定位效果来源。

## 7. 多模态处理

当前实现处理两类图片：

1. 用户上传图片。
2. 手册中的图片。

### 7.1 用户上传图片识别

用户请求中携带图片时，系统会先调用视觉模型生成图片摘要，再把摘要作为用户问题的补充上下文。相关预算：

```env
VISION_MODEL=qwen3.7-plus-2026-05-26
VISION_MAX_IMAGES=6
VISION_MAX_TOKENS=800
```

含义：

- `VISION_MAX_IMAGES`：每个问题最多处理多少张上传图片。
- `VISION_MAX_TOKENS`：每次视觉摘要允许的输出预算。

增加这两个值可能提升多图问题的理解能力，但会增加成本和延迟。

### 7.2 手册图片预处理

手册图片不在默认流程里逐张调用视觉模型离线 caption，而是通过手册文本中的 `<PIC>` 和图片邻近文本建立可检索上下文。

相关配置：

```env
VISUAL_TOP_K=8
VISUAL_CONTEXT_WINDOW=360
```

含义：

- `VISUAL_TOP_K`：图片相关片段召回数量。
- `VISUAL_CONTEXT_WINDOW`：围绕 `<PIC>` 标记截取多少前后文本。

提高 `VISUAL_CONTEXT_WINDOW` 可以让图片片段携带更多说明文字，适合图片前后描述较分散的手册。修改该值会使 retrieval context cache 失效，但不需要重新 `build_index`。

### 7.3 图片输出格式

模型内部可以使用带 ID 的图片引用辅助决策，但最终提交答案中不能裸露图片 ID。系统会把模型答案规范化为：

```text
回答正文 <PIC>,["image_id"]
```

若不需要图片，则不追加图片列表。这样可以减少格式错误和无效图片引用。

## 8. 模型调用策略

### 8.1 默认百炼 / DashScope 路线

默认配置：

```env
CHAT_API_BACKEND=langchain
CHAT_MODEL=qwen3.7-plus-2026-05-26
CHAT_ENABLE_THINKING=false
CHAT_MAX_TOKENS=450
CHAT_THINKING_BUDGET=0
```

默认关闭 thinking，原因是：

- 批量生成更稳定。
- 延迟和 token 成本更低。
- 不容易出现思考内容挤占最终答案预算的问题。
- 之前实验中 thinking 配置不当会导致空答案或大量兜底答案。

如要提高回答完整度，优先增加 `CHAT_MAX_TOKENS` 到 `700` 或 `900`，再考虑 rerank 和上下文预算。

### 8.2 Thinking 消融

如果需要测试 thinking，高预算必须同时打开：

```env
CHAT_ENABLE_THINKING=true
CHAT_THINKING_BUDGET=1024
CHAT_MAX_TOKENS=1200
```

更激进的设置：

```env
CHAT_THINKING_BUDGET=2048
CHAT_MAX_TOKENS=1800
```

thinking 消融应单独使用独立 answers cache，避免与 no-thinking 结果混淆。

### 8.3 OpenAI Responses API 消融

当前也支持可选的 OpenAI Responses API 后端：

```env
CHAT_API_BACKEND=openai_responses
OPENAI_API_KEY=...
OPENAI_RESPONSES_MODEL=gpt-5.5
OPENAI_RESPONSES_REASONING_EFFORT=none
CHAT_MAX_TOKENS=900
```

reasoning 默认关闭。只有在明确做 reasoning 消融时才设置为 `low`、`medium` 或 `high`。

该路径用于横向比较不同基模，不改变本地 RAG 和提交生成流程。

## 9. 提示词策略

当前提示词分为两轮：

1. 生成初稿。
2. 检查与改写。

提示词重点约束：

- 只根据用户问题、用户图片摘要、RAG 证据和通用客服政策回答。
- 不把手册目录、标题、页码、来源标签、无关安全警告复制进答案。
- 不承诺无证据的费用、时效、保修、兼容性、责任归属和绝对结论。
- 步骤类问题压缩为关键步骤，避免整段复述手册。
- 英文问题保持英文回答，中文问题保持中文回答。
- `<PIC>` 只作为图片占位，图片 ID 由后处理统一管理。

这套提示词主要解决幻觉、冗长、格式污染和检索噪声问题。它不能完全弥补错误召回，因此 rerank 和检索预算仍然是重要消融项。

## 10. 缓存与断点续跑

当前有两类主要缓存：

### 10.1 检索上下文缓存

默认路径：

```text
storage/vectorstore/contexts_cache.json
```

作用：

- 缓存每个问题的检索结果。
- 避免重复检索和 rerank。
- 支持不同消融配置使用不同 cache 文件。

会影响缓存签名的因素包括：

- RAG backend。
- embedding 配置。
- `TOP_K`。
- `RETRIEVAL_TOP_K`。
- rerank 配置。
- `VISUAL_TOP_K`。
- `VISUAL_CONTEXT_WINDOW`。
- RAG 上下文格式版本。
- FAISS 检索策略版本。

### 10.2 答案缓存

默认路径：

```text
storage/api_cache/answers_cache.jsonl
```

作用：

- 保存模型调用结果。
- 保存 draft、checked answer、final answer、session id、trace 和 token usage。
- 支持失败后续跑。
- 支持对低质量结果做排查。

会影响答案缓存签名的因素包括：

- chat backend。
- chat model。
- thinking 开关和 thinking budget。
- `CHAT_MAX_TOKENS`。
- prompt hash。
- vision model。
- RAG 上下文格式版本。

做消融时建议显式指定独立缓存文件，避免不同实验互相复用。

## 11. 生成提交的标准流程

### 11.1 准备环境

推荐 conda / pip 路线：

```bash
conda create -n kafu-agent python=3.11 -y
conda activate kafu-agent
python -m pip install -e .
```

如需运行测试：

```bash
python -m pip install -e ".[dev]"
```

如需启用 FAISS dense 检索：

```bash
python -m pip install -e ".[faiss]"
```

默认百炼 API-first 路线不需要安装 `local` extra。

### 11.2 配置 `.env`

核心配置示例：

```env
BAILIAN_API_KEY=your-key
DASHSCOPE_API_KEY=
BAILIAN_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1

CHAT_API_BACKEND=langchain
CHAT_MODEL=qwen3.7-plus-2026-05-26
CHAT_ENABLE_THINKING=false
CHAT_MAX_TOKENS=700
CHAT_THINKING_BUDGET=0

VISION_MODEL=qwen3.7-plus-2026-05-26
VISION_MAX_IMAGES=6
VISION_MAX_TOKENS=800

EMBEDDING_BACKEND=openai
EMBEDDING_MODEL=text-embedding-v4
EMBEDDING_BATCH_SIZE=10

RAG_BACKEND=hybrid
TOP_K=10
RETRIEVAL_TOP_K=40
VISUAL_TOP_K=10
VISUAL_CONTEXT_WINDOW=480

RERANK_ENABLED=true
RERANK_BACKEND=bailian
RERANK_MODEL=qwen3-vl-rerank
RERANK_TOP_N=10
```

### 11.3 构建索引

```bash
python scripts/build_index.py
```

只有以下情况通常需要重新构建索引：

- 首次运行。
- 手册数据变化。
- `CHUNK_SIZE` 或 `CHUNK_OVERLAP` 改变。
- embedding backend、embedding model 或 embedding query prompt 改变。
- `RAG_BACKEND` 在 `hybrid`、`faiss` 或 `llamaindex` 之间切换。

只修改 `TOP_K`、`RETRIEVAL_TOP_K`、rerank、`VISUAL_TOP_K`、`VISUAL_CONTEXT_WINDOW`、chat model 或 prompt 时，通常不需要重新 build index。

### 11.4 生成提交

推荐 no-thinking + rerank 消融命令：

```bash
python scripts/generate_submission.py --workers 6 --retries 3 --force \
  --contexts-cache storage/vectorstore/contexts_cache_rerank_ctx480.json \
  --answers-cache storage/api_cache/answers_cache_rerank_ctx480_nothink.jsonl
```

参数说明：

- `--workers`：并发生成问题数量。API 稳定时可用 `6` 或 `8`，不建议盲目开到 `16`。
- `--retries`：单题失败重试次数。
- `--force`：重新生成答案，不复用已有 `submission.csv` 中的结果。
- `--contexts-cache`：指定检索上下文缓存。
- `--answers-cache`：指定答案缓存。

生成中断时，已完成答案会保存在 `submission.csv` 和 answers cache 中，可根据同一配置继续运行。

## 12. 推荐消融顺序

建议按以下顺序做服务器实验：

1. 基线 no-thinking

   ```bash
   export CHAT_ENABLE_THINKING=false
   export CHAT_MAX_TOKENS=700
   export RERANK_ENABLED=false
   ```

2. no-thinking + rerank

   ```bash
   export CHAT_ENABLE_THINKING=false
   export CHAT_MAX_TOKENS=700
   export RERANK_ENABLED=true
   export RERANK_BACKEND=bailian
   export RERANK_MODEL=qwen3-vl-rerank
   export RETRIEVAL_TOP_K=40
   export RERANK_TOP_N=10
   export TOP_K=10
   ```

3. no-thinking + rerank + 更大图片上下文

   ```bash
   export VISUAL_TOP_K=10
   export VISUAL_CONTEXT_WINDOW=480
   ```

4. thinking 消融

   ```bash
   export CHAT_ENABLE_THINKING=true
   export CHAT_THINKING_BUDGET=1024
   export CHAT_MAX_TOKENS=1200
   ```

5. OpenAI Responses 消融

   ```bash
   export CHAT_API_BACKEND=openai_responses
   export OPENAI_RESPONSES_MODEL=gpt-5.5
   export OPENAI_RESPONSES_REASONING_EFFORT=none
   export CHAT_MAX_TOKENS=900
   ```

每个消融必须使用独立 cache 文件，并记录完整 `.env` 或 export 命令。否则很难判断分数变化来自模型、检索、rerank、prompt 还是缓存复用。

## 13. 提交前健康检查

生成后建议先做格式体检：

```bash
python - <<'PY'
import csv
rows=list(csv.DictReader(open("submission.csv",encoding="utf-8-sig",newline="")))
rets=[r["ret"].strip() for r in rows]
print("rows", len(rows))
print("empty", sum(not s for s in rets))
print("fallback", sum(s.startswith("根据说明，") or s.startswith("According to the available manual information") for s in rets))
print("think_leak", sum("<think" in s.lower() or "reasoning_content" in s for s in rets))
print("api_error", sum(any(x in s for x in ["Traceback","Error code","BadRequest","RuntimeError","InternalError"]) for s in rets))
print("hash", sum("#" in s for s in rets))
print("pic", sum("<PIC>" in s for s in rets))
print("physical_lines", sum(1 for _ in open("submission.csv",encoding="utf-8-sig")))
PY
```

重点关注：

- 是否正好 400 行。
- 是否存在空答案。
- 是否大量出现兜底答案。
- 是否泄露 API 错误或 traceback。
- 是否泄露 thinking 内容。
- 是否包含 Markdown 标题符号。
- `<PIC>` 是否格式正常。
- CSV 物理行数是否异常膨胀。

如答案包含大量换行，可生成归一化版本：

```bash
python - <<'PY'
import csv, re
rows=list(csv.DictReader(open("submission.csv", encoding="utf-8-sig", newline="")))
with open("submission_normalized.csv","w",encoding="utf-8-sig",newline="") as f:
    w=csv.DictWriter(f,fieldnames=["id","ret"])
    w.writeheader()
    for r in rows:
        w.writerow({"id":r["id"],"ret":re.sub(r"\s+"," ",r["ret"].strip())})
PY
```

## 14. 预算项与质量影响

当前最值得调的预算项：

| 配置 | 默认值 | 主要影响 | 建议 |
| --- | --- | --- | --- |
| `CHAT_MAX_TOKENS` | `450` | 最终答案长度 | no-thinking 可试 `700` 或 `900` |
| `TOP_K` | `8` | 进入模型的上下文数量 | 可试 `10` |
| `RETRIEVAL_TOP_K` | `20` | 初始召回候选数量 | 配合 rerank 可试 `40` |
| `RERANK_TOP_N` | `8` | rerank 后保留片段 | 可试 `10` |
| `VISUAL_TOP_K` | `8` | 图片相关片段数量 | 可试 `10` |
| `VISUAL_CONTEXT_WINDOW` | `360` | 手册图片邻近文本长度 | 可试 `480` 或 `640` |
| `VISION_MAX_IMAGES` | `6` | 用户上传图片处理数量 | 多图问题可提高 |
| `VISION_MAX_TOKENS` | `800` | 用户图片摘要长度 | 图像复杂时可提高 |
| `CHAT_THINKING_BUDGET` | `0` | thinking 预算 | 只在 thinking 消融中使用 |

不建议提高：

- `EMBEDDING_BATCH_SIZE`：主要影响速度，百炼接口大于 `10` 可能报错。
- `--workers` 过高：可能导致 API 抖动、超时、空答案或限流。

## 16. 部署边界

### 16.1 默认不需要本地 vLLM

当前默认使用百炼托管模型：

- qwen chat / vision 通过 API 调用。
- embedding 通过 API 调用。
- rerank 可通过 API 调用。

因此不需要本地部署 vLLM，也不需要准备本地 GPU 权重。

### 16.2 什么时候需要 vLLM

只有以下情况才需要考虑 vLLM：

- 使用开源权重本地推理。
- 使用微调后的本地权重。
- 希望绕开托管 API 成本或速率限制。
- 需要完全离线部署。

这不是当前默认比赛提交路线。

## 17. 风险与排查

常见风险：

- thinking 开启但 token 预算不足，导致最终答案为空或大量兜底。
- rerank 或 embedding API 批量过高，引发限流或 BadRequest。
- 检索上下文过多，模型复制手册标题、目录或无关安全提示。
- 图片引用格式被模型污染，出现裸图片 ID。
- 不同消融共用缓存，导致分数变化无法归因。
- `submission.csv` 中含大量换行，人工检查不便。

排查顺序：

1. 先做提交文件健康检查。
2. 看 answers cache 中失败题的 trace。
3. 检查该题 retrieval context 是否召回错误。
4. 如果召回正确但答案错误，调整 prompt 或 `CHAT_MAX_TOKENS`。
5. 如果召回错误，优先调整 `RETRIEVAL_TOP_K`、rerank 和图片上下文预算。
6. 如果大量空答案，降低并发、增加重试和超时，检查模型预算。

## 18. 当前推荐生产配置

在服务器上优先使用以下配置生成一版主提交：

```bash
export CHAT_API_BACKEND=langchain
export CHAT_ENABLE_THINKING=false
export CHAT_MAX_TOKENS=700

export RAG_BACKEND=hybrid
export TOP_K=10
export RETRIEVAL_TOP_K=40
export VISUAL_TOP_K=10
export VISUAL_CONTEXT_WINDOW=480

export RERANK_ENABLED=true
export RERANK_BACKEND=bailian
export RERANK_MODEL=qwen3-vl-rerank
export RERANK_TOP_N=10

python scripts/build_index.py
python scripts/generate_submission.py --workers 6 --retries 3 --force \
  --contexts-cache storage/vectorstore/contexts_cache_rerank_ctx480.json \
  --answers-cache storage/api_cache/answers_cache_rerank_ctx480_nothink.jsonl
```

如果 API 稳定且无空答案，可尝试 `--workers 8`。如果出现超时或空答案，降回 `--workers 4` 到 `6`。

如需做 FAISS 消融，在同一套预算上切换：

```bash
python -m pip install -e ".[faiss]"
export RAG_BACKEND=faiss

python scripts/build_index.py
python scripts/generate_submission.py --workers 6 --retries 3 --force \
  --contexts-cache storage/vectorstore/contexts_cache_faiss_rerank_ctx480.json \
  --answers-cache storage/api_cache/answers_cache_faiss_rerank_ctx480_nothink.jsonl
```

FAISS 消融建议使用独立 contexts cache 和 answers cache，避免和 `RAG_BACKEND=hybrid` 结果混用。
