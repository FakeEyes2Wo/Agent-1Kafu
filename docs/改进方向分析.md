# 改进方向分析

> 范围：基于当前 `main` 分支、仓库文档与 DataFountain 赛题页面（截至 2026-06-05）分析现有设计，并给出可落地的改进路线。
>
> 2026-06-05 更新：后续实现方向已收敛为“尽量依靠百炼 API + 本地
> BM25/sparse 检索”。大模型、视觉理解和可选 dense embedding 使用百炼
> API；手册解析、BM25、RRF、PIC formatter 和 `/chat` 服务在本地应用中完成。

## 1. 前提与成功标准

### 前提

- 当前仓库 `main` 分支是分析对象，不假设未提交的本地代码存在。
- 当前工作区没有比赛数据目录 `data/`，因此本文先给出设计与验证路线，不给出实际榜单分数判断。
- 赛题初赛技术实现评分重点是多模态理解、RAG 检索、多轮记忆与幻觉抑制；系统设计评分重点是模块划分和文档规范。
- 比赛要求最终材料至少包括 `/chat` API、源码、技术文档、验证报告。

### 目标成功标准

1. 代码可以从干净环境复现：依赖安装、索引构建、API 启动、提交生成均可运行。
2. RAG 能稳定命中正确手册片段和图片 ID，尤其是型号、部件、步骤、警示和表格类问题。
3. 回答覆盖用户问题的所有子问题，必要时附 `<PIC>`，且不输出无证据的参数、时效、承诺和图片 ID。
4. 有可重复的离线评估：检索、图片引用、回答质量、延迟与失败率均可量化。
5. 技术文档能清楚解释架构、RAG 策略、多模态策略、幻觉抑制和验证结果。

## 2. 当前设计概览

当前方案意图是一个轻量 LangChain + LangGraph 客服智能体：

```text
data/question_public.csv
data/KownledgeBase/手册/*.txt + data/KownledgeBase/手册/插图/*
        |
        v
build_index.py -> 本地向量索引 / contexts_cache
        |
        v
LangGraph:
  summarize_images -> retrieve_context -> generate_answer -> check_answer
        |
        +-> /chat API
        +-> generate_submission.py -> submission.csv
```

已经具备的设计点：

- `/chat` API 接收 `question/images/session_id/stream`，并使用 Bearer Token 认证。
- `summarize_images` 预留视觉模型摘要能力，最多处理 3 张 Base64 图片。
- `retrieve_context` 支持把图片摘要拼到文本查询中。
- `generate_answer` 与 `check_answer` 分两次模型调用：先生成候选答案，再进行质检改写。
- Prompt 已明确语言规则、证据优先、图片 `<PIC>` 后处理、多子问题逐个回答。
- `generate_submission.py` 支持断点续传、上下文缓存、并发生成和最终格式校验。

## 3. 关键缺口

### P0：RAG 包缺失（已修复）

早期基线曾缺少 `kefu_agent.rag` 实现，但以下位置仍依赖该包：

- `src/kefu_agent/graph.py`
- `scripts/build_index.py`
- `scripts/generate_submission.py`
- `tests/test_rag.py`

当前已重建 `src/kefu_agent/rag/` 包，覆盖手册解析、BM25/sparse、可选 dense、RRF、visual pseudo chunk、PIC formatter 和答案图片 ID 后处理。后续优先级从“恢复 RAG 包”转为补齐测试、服务器消融和文档一致性。

### P0：数据与复现链路缺失

仓库没有 `data/`，且没有数据完整性检查脚本。赛题数据页面给出了三个资源及 MD5，但当前项目只在文档中说明目录结构，没有把以下内容固化为流程：

- 数据文件名和放置路径。
- 手册文本、插图目录、公开问题、提交样例的存在性检查。
- MD5 校验。
- 首次构建索引前的错误提示。

这会影响系统设计分和复现成功率。

### P1：RAG 架构意图与实现对齐

当前实现已按测试表达的设计意图拆成 `kefu_agent.rag.retrieval`、`kefu_agent.rag.visual`、`kefu_agent.rag.images` 等模块，并覆盖 hybrid search、visual retrieve、RRF、图片 ID 校验等能力。包结构为：

```text
src/kefu_agent/rag/
  __init__.py
  schema.py        # Chunk、metadata、版本常量
  parsing.py       # 手册解析、section/chunk、PIC 映射
  embeddings.py    # hash/openai/sentence-transformer
  retrieval.py     # dense/lexical/hybrid/RRF/rerank
  visual.py        # 每张插图构建可检索 pseudo chunk
  images.py        # 图片 ID 验证与答案后处理
  formatting.py    # context 格式化
```

### P1：通用政策路由过粗

`_is_general_policy_question` 用关键词直接绕过手册检索。这个策略对物流、退款、发票等通用题有效，但存在误伤：

- “说明书”既可能是通用客服政策，也可能是具体手册内容检索。
- “保修/质保”既可能是通用售后，也可能是某产品说明书中的具体条款。
- 一个问题可能同时包含通用售后和具体商品故障。

建议把路由从二分类改成三类：`manual`、`policy`、`mixed`。`mixed` 同时取通用政策和手册证据，再由回答生成阶段融合。

### P1：多子问题只在 Prompt 中要求，缺少结构化处理

当前设计把“一行多个子问题”交给 Prompt 处理，风险是漏答、跳答或答案顺序错。应增加轻量问题拆解：

1. 用规则先按换行、中文问号、英文问号、逗号连接句识别候选子问题。
2. 对每个子问题单独检索。
3. 合并 context，并在 prompt 中保留 `子问题1/2/3` 的结构。
4. 质检阶段检查每个子问题是否都有回应。

这比依赖模型自行推断更稳定，也更贴合评分中的“复杂问题拆解”和“多轮对话”。

### P1：图片能力目前偏被动

现有设计能总结用户上传图片，但对手册插图的检索仍主要依赖文本片段里的 `<PIC>`。更高分的方向是把手册插图变成可检索对象：

- 为每个图片 ID 构建 pseudo chunk：来源手册、所在 section、前后文本窗口、图片附近标题。
- 如果可以离线 OCR 或 caption，则把 OCR/caption 加入 pseudo chunk。
- 检索时并行跑文本 chunk 和图片 pseudo chunk，用 RRF 合并。
- 答案后处理只允许输出来自 context 的图片 ID，禁止模型自造。

这样能提升“图片有助理解”和“图文互补”的评分项。

## 4. 分层改进路线

### P0：恢复可运行基线

目标：让项目至少能安装、测试、建索引、生成提交。

建议步骤：

1. 从提交 `2da5697` 恢复旧版 RAG 能力，或按当前测试重建 `src/kefu_agent/rag/` 包。
2. 优先满足当前测试中已经表达的接口：`Chunk`、`build_index`、`retrieve`、`format_contexts`、`format_answer_with_image_list`、`visual_retrieve`、版本常量。
3. 补数据检查脚本或在 `build_index.py` 中前置校验 `question_public.csv`、`submission_example.csv`、`data/KownledgeBase/手册`、插图目录。
4. 运行最小验证：

```powershell
uv sync
uv run pytest -q
uv run python scripts/build_index.py
uv run python scripts/evaluate_retrieval.py --limit 20
```

验收标准：

- `pytest` 不因缺失 `kefu_agent.rag` 失败。
- 无数据时给出明确错误，而不是隐式建空索引。
- 有数据时可以生成索引和 `storage/eval/retrieval_eval.csv`。

### P1：提高 RAG 命中率

目标：提升检索证据质量，尤其是正确手册、正确 section、正确图片 ID。

建议策略：

1. **结构化切块**：按标题、步骤、表格、警告语、列表项切块，而不是单纯固定长度；保留父标题链。
2. **PIC 绑定**：将 `<PIC>` 和图片 ID 绑定到最近的步骤/表格/标题，不让图片漂移到无关 chunk。
3. **混合检索**：dense embedding + lexical BM25/字符 ngram + visual pseudo chunk，使用 Reciprocal Rank Fusion 合并。
4. **重排**：对 top 20-40 候选做 rerank，最终给模型 top 6-10 个高质量 context。
5. **查询增强**：抽取型号、部件、故障、动作词；中英文问题分别走对应语言手册，混合问题保留双语候选。
6. **MMR 去冗余**：避免 top context 全来自同一重复片段，保留不同 section 的证据。

建议离线指标：

- `Recall@k_manual`：正确手册是否出现在 top k。
- `Recall@k_image`：样例答案图片 ID 是否出现在 top k context。
- `PIC Precision`：回答中 `<PIC>` 数量是否匹配有效图片列表。
- `Context Waste`：传给模型的 context 中无关 chunk 占比。

### P1：提高回答质量与幻觉抑制

目标：让 LLM 裁判更容易给 4-5 分。

建议策略：

1. **结构化 evidence block**：不要只拼纯文本，改成 `source/title/text/image_ids/relevance_reason`。
2. **答案模板约束**：按“结论 -> 步骤/依据 -> 下一步”生成，普通通用题短答，说明书题分点。
3. **覆盖检查**：对拆分后的子问题逐项检查是否回答。
4. **证据边界**：没有证据时只请求最少补充信息，不编型号、金额、时效、免费承诺。
5. **图片后处理强约束**：模型只输出裸 `<PIC>`；系统根据 context 顺序追加图片列表。
6. **减少无意义二次调用**：简单问题可跳过 `check_answer` 或改为规则校验，降低延迟；复杂/含图/多子问题再启用质检。

### P2：评估与实验闭环

目标：每次改动都知道是否变好。

建议建立实验矩阵：

| 实验 | 变量 | 观察指标 |
| --- | --- | --- |
| E1 | dense vs dense+lexical | manual/image recall、平均 context 字数 |
| E2 | 无 rerank vs rerank | recall、延迟、回答质量 |
| E3 | 普通 chunk vs section chunk | manual recall、答案完整度 |
| E4 | 无 visual pseudo chunk vs 有 visual pseudo chunk | image recall、PIC precision |
| E5 | 直接问答 vs 子问题拆解检索 | 多子问题覆盖率 |
| E6 | 一次生成 vs 生成+质检 | LLM 裁判分、延迟、成本 |

验证报告中可以使用：

- `scripts/evaluate_retrieval.py` 输出检索统计。
- 抽样 30-50 道题人工标注正确手册/图片。
- DataFountain A 榜提交分数作为最终外部指标。
- API 压测：文本 20s 内、含图 30s 内。

### P2：API 与工程化

建议补强：

- `/chat` 请求校验图片数量、Base64 前缀、单图大小。
- 日志记录 `request_id/session_id/query_type/top_context_ids/latency/model_error`，不要记录完整敏感图片。
- 增加 `/debug/retrieve`，仅本地或 token 管理员可用，用于快速查看检索证据。
- 增加模型错误重试和降级策略：视觉失败不阻断文本回答；检索失败时提示无法确认。
- 明确 `stream=false` 当前只是兼容字段，不实现 SSE；若实现流式，需要同步调整评测接口说明。

## 5. 不建议优先做的事

- 不建议先做在线微调：当前缺少可运行 RAG 和离线评估，微调成本高且难验证。
- 不建议先做复杂 Web UI：赛题主要评 API 和提交文件，UI 对分数贡献小。
- 不建议引入 Milvus/分布式向量库：数据规模不大，本地 FAISS/JSONL/llama-index 足够；先解决检索质量。
- 不建议把通用政策写得太“客服话术化”：无证据承诺越多，越容易被幻觉扣分。

## 6. 推荐优先级

### 第 1 天：救活工程

1. 重建 `src/kefu_agent/rag/` 包。
2. 让现有测试至少通过与 RAG 相关的导入和核心后处理。
3. 加数据存在性与 MD5 校验。

### 第 2-3 天：提升检索

1. 实现 section-aware chunk。
2. 实现 dense + lexical + visual RRF。
3. 接入 rerank，并用 `evaluate_retrieval.py` 做 ablation。

### 第 4-5 天：提升回答

1. 加子问题拆解和 per-subquestion retrieval。
2. 优化 prompt 为结构化 context。
3. 强化图片后处理和通用/手册/mixed 路由。

### 第 6 天：验证与文档

1. 生成 A 榜提交，记录外部分数。
2. 完成验证报告：检索指标、回答样例、失败案例和优化前后对比。
3. 更新技术文档和接口说明，确保与代码一致。
